Execution Runtimes (Backends)

The model weights are always Typhoon Whisper (Turbo or Large-v3); what changes across runtimes is the execution engine and the hardware processor running it.

Why does the runtime matter? Whisper inference is computationally heavy. On an Intel Core Ultra 5 125H box, plain PyTorch CPU float32 is slow (RTF > 1.0, falls behind live speech). It uses none of what the hardware offers: no int8, no iGPU, no vector instructions. whisper.cpp (GGML Q5_0), CTranslate2 (int8 with AVX-VNNI) and OpenVINO (Intel Arc iGPU) each use a different part of it, which is why the right choice is machine-specific — and why the answer comes from measuring, not from a table.

1. PyTorch (pytorch)

Default Apple MPS / CPU float32

Standard implementation using Hugging Face transformers and torch.

  • On Apple Silicon (Mac): Uses Apple Metal Performance Shaders (MPS GPU). Extremely fast and responsive due to unified memory architecture.
  • On Intel/AMD x86 (Linux/Windows): Runs on CPU in float32. Does not use int8 quantization, tensor cores, or integrated GPU acceleration.
  • Conversion: Zero conversion required. Downloads directly from Hugging Face Hub on first load.
  • Best for: Development on Mac, or as an absolute accuracy baseline. On Intel Core Ultra boxes, this is the slowest option.

2. whisper.cpp (whispercpp)

Recommended CPU Engine GGML Q5_0 Quantization

High-performance pure C/C++ port of OpenAI Whisper developed by Georgi Gerganov, bound via pywhispercpp.

  • Weight format: 5-bit integer quantized GGML weights (q5_0). Model file size is only 574 MB (Turbo), cutting memory bandwidth dramatically.
  • Hardware Acceleration: Uses CPU vector SIMD instructions (AVX, AVX2, AVX-VNNI on x86, Metal on macOS). Zero Python runtime overhead during active transcription passes.
  • Decoding: Configured with greedy decoding (temperature=0.0) and silent window termination to eliminate synthetic hallucinations.
  • Conversion command: uv run python convert_model.py --runtime whispercpp --model turbo (downloads community GGML weights from Hugging Face).
  • Best for: Fast CPU inference with minimal RAM usage, robust behavior on silence.

3. CTranslate2 (ctranslate2)

Recommended for AVX-VNNI int8 Quantization

Custom C++ inference engine specifically designed for Transformer models, used through faster-whisper.

  • Weight format: 8-bit integer quantization (int8).
  • Hardware Acceleration: Heavily accelerated on modern Intel CPUs equipped with AVX-VNNI (Vector Neural Network Instructions) like Intel Meteor Lake (Core Ultra 5 125H).
  • Optimized Decoding: Uses beam_size=1, temperature=0.0, and condition_on_previous_text=False to avoid 6-pass escalating temperature loops during synthetic/silent audio.
  • Conversion command: uv run python convert_model.py --runtime ctranslate2 --model turbo.
  • Best for: Intel Core Ultra CPUs when running CPU inference with AVX-VNNI.

4. OpenVINO GPU (openvino-gpu)

Recommended for Intel Arc iGPU Intel Xe / Arc iGPU

Intel OpenVINO runtime compiled specifically for Intel integrated graphics (GPU.0 / renderD128).

  • Offload Strategy: Offloads the heavy matrix multiplications of Whisper completely to the Intel Arc integrated GPU.
  • CPU Relief: Keeps host CPU utilization minimal, leaving all CPU cores free for host applications, databases, or speech pipelines.
  • Conversion command: uv run python convert_model.py --runtime openvino --model turbo.
  • Best for: Advantech UBX-330M and Intel Core Ultra devices when you want GPU offloading.

5. OpenVINO CPU (openvino-cpu)

Intel CPU Vector Pipeline

Intel OpenVINO runtime optimized for Intel CPU vector instruction pipelines (AVX2, AVX-512, AMX).

  • Shares the same converted OpenVINO model directory as openvino-gpu.
  • Executes on the CPU if an integrated GPU is busy or unavailable.

Checking…

Models you can run

The Model field is discovered on this machine, not a fixed list. It combines the two builtin Typhoon fine-tunes, anything in models.local.json, every Whisper model already in the Hugging Face cache, and any weights converted into models/. Install a model and hit Rescan in the panel — no restart.

Adding a model. Either download it (hf download openai/whisper-small) and it appears by itself, or name it in models.local.json as {"my-key": "org/repo"} to have it downloaded on first use. Two things stay true however long the list gets: whispercpp can only load a model with GGML weights, and an English-only Whisper (whisper-*.en) refuses a pinned language — the panel flags those and the server declines the combination rather than failing partway through a session.

turbo

Default 4 decoder layers

typhoon-ai/typhoon-whisper-turbo — a fine-tune of whisper-large-v3-turbo. The encoder is full size; the decoder is cut from 32 layers to 4, which is where nearly all the speed comes from.

Runs on every runtime, and it is the only model with a published GGML build, so it is the only one whispercpp can load without extra work.

Converted sizes measured on this machine: 547 MB as GGML q5_0, 781 MB as CTranslate2 int8.

large-v3

32 decoder layers No GGML build

typhoon-ai/typhoon-whisper-large-v3 — a fine-tune of full whisper-large-v3. The full decoder is kept, so it has more to work with on difficult audio: heavy accents, overlapping speakers, unfamiliar vocabulary. It also has roughly eight times the decoder to run per chunk.

Works on pytorch, ctranslate2 and both OpenVINO runtimes once converted. For whispercpp you would have to build the GGML weights yourself — see the whispercpp card below.

Which one? Start with turbo. It is the one this project was built around, the one every runtime supports, and the only one with any chance of keeping RTF under 1.0 on modest hardware. Reach for large-v3 only when you have evidence that turbo is mis-transcribing the words you care about — replay the same clip through both and compare the transcripts, not just the timings.

Any Whisper-architecture repo on Hugging Face should load on pytorch; the other runtimes need their own conversion pass first. A model for another language needs no code change — pick that language in the Language field.

Preparing each runtime

Two things have to be true before a runtime turns green: its library is installed, and the weights are converted into its format. Conversion happens once per machine and lands in models/.

pytorch

Nothing to do

Installed with the project and runs the Hugging Face weights directly, so it is always available. The first run downloads the model.

Keep it as the accuracy baseline. On the UBX-330M it is the slowest option — that is expected, not a fault.

ctranslate2

Verified working int8 · CPU

faster-whisper is already a project dependency, so only the conversion is needed:

uv sync
uv run python convert_model.py --runtime ctranslate2 --model turbo

Conversion downloads the model and re-encodes it to int8, so expect several GB and a few minutes. It was the step most likely to fail — Typhoon is a fine-tune rather than stock Whisper — but it converts cleanly and transcribes Thai correctly.

whispercpp

Verified working GGML · CPU

pywhispercpp is already a project dependency. This runtime does not convert anything — it downloads a GGML build somebody else made:

uv sync
uv run python convert_model.py --runtime whispercpp --model turbo

Two things to know. The weights come from korakotlee/typhoon-whisper-turbo-ggml, a community conversion, not a build published by typhoon-ai — if its accuracy drifts noticeably from pytorch on the same clip, suspect the conversion before you suspect the engine. And only turbo has a published build.

For large-v3, convert it yourself with whisper.cpp's models/convert-h5-to-ggml.py and drop the resulting .bin into models/whispercpp-large-v3/. The probe picks up any .bin it finds there.

openvino-gpu · openvino-cpu

Fastest on the UBX-330M Intel only

OpenVINO is deliberately not installed by default — it is only useful on an Intel machine, so it lives behind an extra:

uv sync --extra openvino
uv run python convert_model.py --runtime openvino --model turbo

One conversion serves both runtimes: it writes models/openvino-gpu-turbo and models/openvino-cpu-turbo with identical contents, and the device is chosen when the model loads. openvino-gpu additionally requires an Intel render node at /dev/dri/renderD*, which the UBX-330M has and no Mac ever will, plus an OpenCL runtime for that node (sudo apt install intel-opencl-icd) plus membership of the render group (sudo usermod -aG render $USER, then log in again). Miss either and the failure looks identical — the node is still listed, OpenVINO reports CPU only, and the panel greys the GPU out with the reason.

Measured on the UBX-330M (Core Ultra 5 125H), one fixed 21s clip in 5s chunks: openvino-gpu mean RTF 0.60 — the only runtime on that box that keeps up with live speech — against 1.34 for ctranslate2 int8 and 2.53 for openvino-cpu running the very same fp32 IR.

Checking your work

Two commands answer "did that work?" without starting a session.

uv run python runtimes.py      # what's ready, and why the rest aren't
uv run python check_hardware.py  # CPU, AVX-VNNI, iGPU, NPU, thread count
Then measure, don't guess. Once two or more runtimes are green, compare them in Benchmark Studio against one fixed clip. Comparing two live microphone sessions tells you nothing: on one machine RTF ranged from 0.48 to 1.90 purely because of how densely the speaker was talking.

Benchmark Studio

How to accurately measure, compare, and verify execution performance.

Why Fixed-Clip Benchmarking?

A live microphone session cannot be compared mathematically against another live session: you speak with different cadence, different pauses, and different words every time. A run that looks faster might simply mean you spoke less.

Benchmark Studio replays a fixed audio clip through the exact same 5-second chunking and 1-second overlap pipeline that the live mic session uses. Because the audio feed is strictly identical across runs, timing differences reflect true hardware throughput.

Recording Benchmark Clips

You can record a reference test clip directly without third-party recording software:

  • On Web GUI: Click the Record button next to the clip dropdown. You can choose between:
    • Browser Mic: Records audio from your laptop or phone over the network with a live audio level (VU) meter.
    • Server Mic: Records directly from the microphone plugged into the host device (e.g. Jabra SPEAK 510 or Logitech Brio on UBX-330M).
    The audio is automatically converted to 16kHz mono WAV and saved to audio/ on the server.
  • On CLI Terminal: Run benchmark.py with --record: 
    uv run python benchmark.py --model turbo --record test_clip.wav --duration 10

Interpreting Benchmark Results

  • 🏆 Winner Banner: Identifies the fastest runtime and calculates the speedup factor over baseline PyTorch (e.g. 3.5× faster than PyTorch).
  • Real-Time Factor (RTF): Latency divided by chunk duration (5s).
    • RTF < 1.0 (Green): Real-time capable. Transcription finishes faster than speech arrives.
    • RTF ≥ 1.0 (Red): Slower than real-time. Lag accumulates with longer sessions.
  • Worst RTF: The longest time taken on any individual chunk in the clip. Crucial for detecting thermal throttling or cold-start spikes.
  • Sample Transcript: Preview of the transcribed Thai text to confirm accuracy wasn't compromised by aggressive quantization.

CPU Thread Pinning on Hybrid Architectures

On hybrid Intel CPUs (such as the Core Ultra 5 125H with 4 P-cores, 8 E-cores, and 2 LP E-cores), using all 14 cores can actually be slower than using only the Performance cores, because slower E-cores delay thread synchronization barriers.

Use taskset to isolate inference to Performance cores:

# Pin to P-core threads (CPUs 0-7) with 8 threads:
taskset -c 0-7 uv run python benchmark.py --model turbo --file audio/clip.wav --threads 8

How a Session Works

Explains why the live readings and chunk outputs behave the way they do.

Whisper models (typhoon-whisper-turbo and typhoon-whisper-large-v3) do not have native streaming architecture: they accept a complete audio tensor, not an unbounded audio stream. Live transcription is achieved by windowing incoming audio into 5-second slices that overlap by 1 second, transcribing each window as soon as it fills.

window 1 · 0–5s0–5s
window 2 · 4–9s4–9s
window 3 · 8–13s8–13s
0s 4s 8s 12s 16s

Each window starts 4 seconds after the last, so consecutive windows share 1 second of audio.

The 1-Second Boundary Overlap

The 1-second overlap guarantees that words spoken across window boundaries aren't sliced in half. The consequence: words spoken during the overlap will legitimately appear at the end of one chunk and the beginning of the next chunk. This is expected behavior and demonstrates that no audio is dropped.

Full-Clip Reference Pass

When you press Stop recording, the entire captured audio file is transcribed once more in a single batch pass, rendered as Full clip. Having the entire speech context allows the model to achieve its highest accuracy, allowing you to evaluate how close the chunked live stream was to the ground truth.

Status Rail Readings & Gauges

The instruments displayed across the top rail of the main interface.

Real-time factor (RTF)

latency ÷ 5.0s

The definitive metric of real-time speech capability. It is the time taken to transcribe a chunk divided by the audio duration of that chunk (5 seconds).

0.54 Transcribed in 2.7s. Keeping up comfortably with live speech.
1.63 Transcribed in 8.1s. Falling behind — backlog increases continuously.

The pale vertical line across the meter marks 1.0 (break-even). Below 1.0, transcription finishes before new speech finishes arriving. At or above 1.0, the pipeline falls progressively behind.

Position

mm:ss

The timestamp of the beginning of the most recent audio chunk. It advances in 4-second steps (00:00, 00:04, 00:08...) corresponding to window start offsets.

Chunks

Total count of 5-second slices processed during the current session, including silent chunks that were skipped.

Keywords

Number of keyword detection events caught and reported to the backend. Duplicate occurrences within the overlap period are suppressed automatically.

Setup Controls & Parameters

Settings applied when starting new live sessions or replaying audio.

Model

turbolarge-v3

turbo: 4 decoder layers. Fast and light; the default, and the only model every runtime can load.

large-v3: 32 decoder layers. More to work with on difficult Thai speech, at roughly eight times the decoder work per chunk.

Full details, including what each model needs per runtime, are under Runtime Setup.

Silence threshold

default 0.02

Audio energy floor calculated via Root Mean Square (RMS). Chunks with audio energy below this threshold are skipped and logged as silence — skipped.

Whisper models lack an explicit "silence" token; when presented with low-level background noise or room tone, they tend to hallucinate plausible Thai text or loop repetitive phrases. Energy gating filters this noise out before sending audio to the model.

Raise to 0.03–0.04 if ambient room noise triggers false text. Lower to 0.01 if quiet or whisper-level speech is being missed.

Language

default Thai

The language the model is told to transcribe. It is passed to whichever runtime is selected, so the setting means the same thing across all five.

Auto-detect hands the decision to the model instead — and it decides per 5-second chunk, not once per session. A chunk of noise, a half-finished word, or a run of English loanwords can be read as another language, and Whisper will then translate that chunk rather than transcribe it. Keyword spotting matches exact substrings, so a translated chunk silently stops matching.

Pin the language unless you genuinely need mixed-language audio. Auto-detect also adds a detection pass per chunk, which makes benchmark timings noisier.

Keywords

Comma-separated list of target Thai words or phrases (e.g. สวัสดี, ขอบคุณครับ). Matches are exact substring matches, case-insensitive.

Detections within ~4.5 seconds are debounced to prevent a single spoken word located in a boundary overlap from firing twice.

Input Device & Rescan

Selects the active microphone device. Click Rescan if you plug in a USB mic (e.g. Jabra SPEAK 510) or pair a Bluetooth headset after the server has already started.

Backend URL

HTTP destination where keyword events are dispatched (default: http://localhost:8000). If the backend is offline, transcription continues without interruption.

When Something Looks Wrong

Common symptoms, underlying causes, and corrective actions.

Observed Symptom Root Cause & Resolution
Words appear while nobody is speaking Ambient room noise or microphone gain is exceeding the silence gate. Increase Silence threshold from 0.02 to 0.03 or 0.04.
Quiet speech is skipped Microphone input gain is too low or mouth is far from mic. Lower Silence threshold to 0.01 or increase OS mic input volume.
Runtime is disabled / greyed out in dropdown Model weights have not been converted for this backend yet. Run the corresponding conversion script (e.g. uv run python convert_model.py --runtime whispercpp --model turbo).
Real-time factor sits above 1.0 (Meter red) Processing latency is slower than audio duration. Switch to a faster runtime (whispercpp, ctranslate2, or openvino-gpu), switch to the turbo model, or pin threads.
The same word appears at the end of one line and start of next Normal behavior. Consecutive 5-second windows share 1 second of overlap audio to prevent split words.
Keyword was spoken but not detected Check the transcribed chunk text — if the model transcribed with different spelling or phrasing, exact substring matching won't trigger. Also check if it fired within the 4.5s debounce window.
Microphone not found in input list Device was plugged in after server started, or missing OS microphone permissions. Click Rescan in the setup panel.
Stopping takes a few seconds The server waits for the current chunk inference pass to complete cleanly, then generates the full-clip reference transcript.
