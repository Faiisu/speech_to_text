Typhoon Whisper Reference ← Back to panel

This rig listens through a microphone and transcribes Thai speech in 5-second slices while you're still talking, flagging any keyword you've asked it to watch for.

Everything below explains what each control changes and what each reading is telling you.

How a session works

Worth reading first — it explains why the readings behave the way they do.

The models behind this (typhoon-whisper-turbo and typhoon-whisper-large-v3) have no streaming mode: they transcribe a finished clip, not a running microphone. So live transcription is faked by slicing the incoming audio into 5-second windows that overlap by 1 second, and transcribing each window as soon as it fills.

window 1 · 0–5s0–5s
window 2 · 4–9s4–9s
window 3 · 8–13s8–13s
0s 4s 8s 12s 16s

Each window starts 4 seconds after the last, so consecutive windows share 1 second of audio.

That 1-second overlap exists so a word spoken right on a boundary isn't sliced in half — it lands whole in at least one window. The cost: audio in the overlap is transcribed twice, so the same word can legitimately appear at the end of one line and the start of the next. That's expected, not a fault. Lines are never stitched together or de-duplicated.

When you press stop, the whole recording is transcribed once more in a single pass and shown as Full clip. With the entire recording as context it's usually the more accurate version — compare it against the live lines to see what the chunking cost you.

Readings

The rail across the top of the panel, left to right.

Real-time factor

latency ÷ 5s

The one number that answers can this keep up with live speech? It's how long a window took to transcribe, divided by the 5 seconds of audio it covered.

0.54 Transcribed in 2.7s. Keeping up comfortably.
1.63 Transcribed in 8.1s. Falling behind — lag grows the longer you talk.

The pale line across the middle of the meter marks 1.0, the break-even point. Below it, transcription finishes faster than you speak. At or above it, each window takes longer than the audio it covers, so the transcript drifts further behind real time the longer the session runs. The meter tops out at 2.0.

Expect this to move a lot: a window packed with continuous speech takes far longer than a window with one short phrase, because there are more words to generate. Test with the busiest speech you actually expect, not short test phrases.

Position

mm:ss

Where the most recent window starts within the recording — not a clock of how long you've been recording. It advances in 4-second steps (00:00, 00:04, 00:08…) because that's the spacing between window starts.

If the model is running slower than real time, Position lags behind wall-clock time. That gap is the transcript falling behind, and it's the same thing the real-time factor is warning you about.

Chunks

How many windows have been handled this session, including ones skipped as silence. Roughly one every 4 seconds of recording.

Keywords

How many keyword detections have fired this session, after duplicate suppression. Each one is also sent to the backend to be recorded.

This counts detections, not distinct words — one keyword caught three times counts as three.

Setup

Changes apply to the next recording you start, not the one already running.

Model

turbo is the smaller, faster model — fewer decoder layers, so less time per window and a lower real-time factor. large-v3 is the full-size model: slower, generally more accurate on hard audio. Both are Thai fine-tunes of Whisper.

Switching models the first time costs a download; after that the model is cached on disk, and stays in memory for the rest of the server run. Only the first session on each model waits for loading.

Keywords

Comma-separated words or phrases to watch for, e.g. สวัสดี, ขอบคุณครับ. Each window's transcript is checked for each one as plain text containment, case-insensitive. Leave it empty to just transcribe and record nothing.

Matching is literal: it finds the characters you typed, so it only fires if the model transcribed the word the way you spelled it. It won't catch near-misses or alternate spellings.

A keyword caught twice within about 4.5 seconds only reports once. The overlap between windows means one spoken word can show up in two consecutive transcripts, and this stops that being counted twice — the trade-off is that genuinely saying the same word twice in quick succession also reports once.

Input

Which microphone to record from. System default uses whatever the OS has selected.

Connected a USB mic or paired a Bluetooth headset after starting the server? Press Rescan — the audio layer caches its device list at startup, so reloading the page alone won't reveal it. Rescan is unavailable mid-session because it resets that audio layer.

Silence threshold

default 0.01

A loudness floor. Windows quieter than this are skipped entirely and never reach the model — shown as silence — skipped.

This exists because these models have no way to output "nothing was said". Fed silence or room tone, they invent plausible text instead, which would produce phantom transcripts and false keyword hits. Gating on loudness first is what prevents that.

Raise it if words appear while nobody is speaking — your room's noise floor is above the current setting. Lower it if quiet speech is being skipped. There's no universal correct value: it depends on the microphone's gain and how noisy the room is.

Backend

Where keyword detections get sent to be stored, so you can count and query them later. Each detection is recorded with the word, the time, which model found it, and which session it came from.

If it's unreachable, recording carries on and a warning appears in the feed — detections are simply not recorded. Transcription never depends on it.

When something looks wrong

What you seeWhat it means
Words appear while nobody is speaking Room noise is clearing the silence threshold and reaching the model, which then invents text. Raise the silence threshold.
The same word ends one line and starts the next Normal. Consecutive windows share 1 second of audio and lines are never stitched together.
Real-time factor sits above 1.0 Windows take longer to transcribe than the audio they cover, so the transcript falls progressively behind. Try the turbo model, or accept the lag if you only need the transcript afterwards.
A keyword you clearly said wasn't flagged Either the model transcribed it differently from how you spelled it — check the line it should have matched — or it was suppressed as a duplicate within ~4.5 seconds of the previous hit.
A warning about reaching the backend The backend URL is wrong or the service isn't running. Recording is unaffected; only the record of detections is lost.
Stopping takes a few seconds The window being transcribed has to finish first, then the whole recording is transcribed once more for the full-clip version.
No microphones in the Input list Nothing is connected, or the process lacks microphone permission. Connect a mic and press Rescan.
